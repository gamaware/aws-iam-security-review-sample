# ADR 0005: Markdown is the canonical report; the shared pipeline builds the PDF

## Status

Accepted

## Context

Clients read a security review as a PDF: they forward it, attach it to an audit request and print it. Engineers
review it as text: they diff a finding, check a quoted line against the evidence, and comment on a pull request.
Keeping two hand-edited copies lets them drift. A PDF rendered by a different engine on each machine drifts in
layout as well.

## Decision

`report/REPORT.md` and `report/control-evidence-map.md` are the only sources. The shared `report.yml` workflow from
`gamaware/.github` renders them into one PDF with its pinned `pandoc/latex` image and the xelatex engine on every CI
run. `make report` runs the same image with the same arguments and writes `report/REPORT.pdf`, which is committed
so a reader can open it without a CI login. No other PDF engine is used.

## Consequences

- The tests that tie the report to the evidence run on the text the client receives.
- A reader browsing GitHub gets the Markdown and the committed PDF; CI also publishes the PDF as an artifact.
- The committed PDF is regenerated by hand after the Markdown changes. It is not byte-reproducible, so no check
  compares it with a fresh build; a stale PDF shows up in review when `report/` changes without it.
- `make report` needs Docker locally, not pandoc or a TeX installation.

## Compliance

- `.gitignore` excludes `build/` and every PDF except `report/REPORT.pdf`.
- The CI report job fails if pandoc cannot render the Markdown.
- `tests/test_report.py` checks the Markdown's quotes, counts, finding IDs, links and fictional label.

## Notes

Pandoc reads both files in order, so the control map becomes the PDF's appendix.
